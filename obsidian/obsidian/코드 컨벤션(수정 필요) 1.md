# 코드 컨벤션 (NGO 멀티플레이)

> 기존 컨벤션에 Unity Netcode for GameObjects(NGO) 멀티플레이 환경을 반영한 통합본입니다. **[변경]** 은 기존 규칙에서 바뀐 항목, **[신규]** 는 이번에 추가된 항목입니다. 이 문서와 충돌하는 규칙이 생기면 **팀 합의 후 이 문서를 먼저 고치고** 코드를 고칩니다.

---

## 0. 대원칙

1. **NGO의 강제 사항이 팀 컨벤션보다 우선한다.** (예: RPC 메서드 접미어)
2. **읽는 사람이 "이 코드가 어디서 실행되는지" 바로 알 수 있게 쓴다.** 
   (서버 / 클라이언트 / 로컬)
3. **의심스러우면 서버를 믿는다.** 판정과 상태 변경은 서버에서 한다.
4. 규칙이 작업을 막으면 우회하지 말고 **문서를 고친다.**

---

## 1. 기술 스택 / 기본 방침

- **네트워크: Unity Netcode for GameObjects (NGO)**, 인터넷 연결은 **Unity Relay + Lobby**
- **Addressables** 사용 — **단, 네트워크 오브젝트는 제외** (3장 참조)
- **UniTask** 사용
- UI 텍스트는 `TextMeshProUGUI`, 버튼은 `Button-TMP`
- 써드파티 사용 전 **상업적 이용 가능 여부 확인 + 라이선스 화면 스크린샷을 디스코드에 공유**
    - **[변경]** 범위에 **폰트, 효과음, 제시어 단어 목록의 출처**까지 포함한다.

### [변경] 프리팹 / 동적 생성 방침

기존의 "씬의 모든 것은 프리팹으로 구성, 동적 생성" 방침은 **비네트워크 오브젝트에만** 적용한다.

|대상|방침|
|---|---|
|UI, 이펙트, 사운드 등 비네트워크 에셋|Addressables로 동적 로드 (기존 방침 유지)|
|`NetworkObject`가 붙은 프리팹|**Addressables 제외.** NetworkManager의 네트워크 프리팹 목록에 **정적 등록**|
|네트워크 매니저류 (`GameStateManager` 등)|**씬에 직접 배치** (씬 배치 NetworkObject는 자동 스폰됨)|

> **이유:** 호스트와 클라이언트의 네트워크 프리팹 목록이 완전히 동일해야 하며, 런타임 등록은 순서까지 맞춰야 해서 추적이 어려운 버그를 만든다.

## 2. 네이밍

### 공통

|대상|규칙|예시|
|---|---|---|
|유니티 오브젝트 참조 필드|`타입_이름`|`Image_AAA`, `Prefab_AAA`, `Transform_AAA`|
|순수 데이터 private 필드|`_카멜케이스`|`_speed`|
|프로퍼티|파스칼케이스|`SoundName { get; private set; }`|
|이벤트|`On + 동사`|`OnChangeCurrency`, `OnStartGame`|
|버튼 연결 메서드|`OnClick + 동사`|`OnClickBuild`|
|일반 메서드|`동사 + 대상`|`GetSize`, `ChangeName`, `MovePlayer`|
|bool 반환 함수|가능하면 `Is` 접두어|`IsAffordable`, `IsPlaceable` (`Try~`는 예외)|

### [신규] 네트워크 관련 네이밍

|대상|규칙|예시|
|---|---|---|
|RPC 메서드|**`Rpc` 접미어 필수** (NGO 1.x는 `ServerRpc` / `ClientRpc`)|`SubmitAnswerRpc`, `BroadcastStrokeRpc`|
|서버에서만 실행되는 메서드|`Server` 접두어|`ServerStartRound`, `ServerValidateAnswer`|
|로컬에서만 실행되는 메서드|`Local` 접두어|`LocalPreviewStroke`|
|`NetworkVariable` 필드|**파스칼케이스 public 필드 허용** (예외)|`public NetworkVariable<int> Score`|
|네트워크 전송용 구조체|`Payload` 접미어 + `INetworkSerializable`|`StrokePayload`, `ScorePayload`|

> **예외 사유:** `NetworkVariable`은 인스펙터 노출과 스폰 처리를 위해 public 필드로 선언하는 것이 NGO의 일반적인 형태다. `_카멜케이스` 규칙을 적용하지 않는다.

## 3. 문법 규칙

- **람다 금지.** `ToDictionary(x => ...)` 같은 LINQ도 `foreach`로 푼다.
- **제네릭 우선** (Array 대신 `List<T>` 등)
- 다른 사람이 쓸 확률이 높은 메서드에는 주석
- 싱글톤 접근자는 `.Inst` (`.Instance` 아님)
    - **[변경]** **우리가 만든 클래스에만 적용.** 외부 라이브러리(NGO의 `NetworkManager.Singleton`, UGS 등)는 원래 이름을 그대로 쓴다.

### [변경] 람다 금지 규칙의 예외

다음은 람다가 아니므로 허용한다.

- 프로퍼티 표현식 본문: `get => _field;` (기존 예외 유지)
- `async` / `await`, UniTask의 `await` 표현

**이벤트·콜백 구독은 반드시 명명 메서드로 한다.** 구독 해제를 위해서도 필요하다.

```csharp
// 금지
Phase.OnValueChanged += (prev, next) => timerText.text = next.ToString();

// 권장
public override void OnNetworkSpawn()
{
    Phase.OnValueChanged += HandlePhaseChanged;
}
public override void OnNetworkDespawn()
{
    Phase.OnValueChanged -= HandlePhaseChanged;
}
private void HandlePhaseChanged(GamePhase prev, GamePhase next) { ... }
```

## 4. 데이터 (JSON) 규칙

- **[변경] 데이터 클래스는 기능별 파일로 나눈다.** `GameData.Word.cs`, `GameData.Player.cs` 형태로 `partial class` 또는 별도 파일을 쓴다.
    - _사유: 세로 슬라이스로 병렬 작업하므로 단일 공용 파일은 충돌 지점이 된다. 파일을 나눠도 `JsonUtility` 동작에는 영향이 없다._
- `GameDataBase` 상속 + `[Serializable]` + **public 필드**(프로퍼티 아님, `JsonUtility` 규칙)
- ID 필드는 `ID` (대문자 둘)
- JSON은 최상위 배열, 매니저가 `{"datas":...}`로 래핑해서 `JsonUtility`로 읽음
- enum은 JSON에 문자열로 저장 → 코드에서 변환 메서드로 파싱
- 조회는 `GameDataManager.Inst.GetData<T>(id)` 제네릭 창구로 통일
- 로드 등록은 `LoadAllData()`에 `LoadData<T>("테이블명")` 한 줄 추가
- JSON 경로: `Assets/Resources/JsonOutput/`
    - **[변경]** **데이터 JSON은 Resources, 에셋은 Addressables**로 역할을 나눈다. 규모가 작아 데이터까지 Addressables로 옮길 이득이 없다.

## 5. MVVM 규칙

- 뷰모델은 `ViewModelBase` 상속 (`INotifyPropertyChanged` 기반)
- 뷰는 `ViewBase`(`MonoBehaviour`) 상속
- 서비스(순수 C#)가 뷰모델을 `new` 생성·보관 → 뷰가 받아 바인딩
- 프로퍼티 변경 시 `OnPropertyChanged(nameof(프로퍼티))` 방송, setter에 `if (_field != value)` 검사

### [신규] 네트워크와 MVVM의 경계

```
NetworkBehaviour   (NetworkVariable / RPC)
      │  OnValueChanged → 명명 메서드
      ▼
  Service          (순수 C#, 뷰모델 생성·보관)
      │  프로퍼티 대입
      ▼
  ViewModel        (INotifyPropertyChanged)
      │  OnPropertyChanged
      ▼
    View           (MonoBehaviour)
```

- **뷰와 뷰모델은 NGO 타입을 참조하지 않는다.** (`NetworkVariable`, `NetworkBehaviour`, RPC 등)
- 네트워크 → 뷰모델 방향은 **서비스가 중계**한다.
- 뷰의 입력은 **서비스의 공개 메서드**를 호출하고, 서비스가 RPC를 부른다.

> **이점:** 뷰와 뷰모델을 네트워크 없이 단독으로 실행·테스트할 수 있어, 두 사람이 서로를 기다리지 않고 작업할 수 있다.

## 6. [신규] 네트워크 규칙

1. **권한을 이름으로 드러낸다.** 서버 전용은 `Server` 접두어, 로컬 전용은 `Local` 접두어. (2장 참조)
2. **모든 RPC의 첫 줄은 검증이다.** 현재 페이즈가 맞는지, 호출자가 권한이 있는지 확인하고 아니면 `return`. 핵 방지뿐 아니라 타이밍 버그를 잡아 준다.
3. **`NetworkVariable`의 쓰기 권한은 기본 Server**로 명시해 선언한다. 클라이언트 쓰기가 필요하면 PR 본문에 이유를 적는다.
    
    ```csharp
    public NetworkVariable<GamePhase> Phase = new(    GamePhase.Waiting,    NetworkVariableReadPermission.Everyone,    NetworkVariableWritePermission.Server);
    ```
    
4. **`NetworkVariable<string>`은 사용 불가.** `FixedString64Bytes` 등을 쓰거나, 긴 텍스트는 RPC로 보낸다.
5. **네트워크 전송 구조체는 `INetworkSerializable` 구현 + `Payload` 접미어.**
6. **전송 빈도·네트워크 상수는 `NetworkConfig.cs` 한 곳에 모은다.** (예: `StrokeSendInterval = 0.05f`) 매직 넘버를 각자 코드에 흩뿌리지 않는다.
7. **시간 기준은 `NetworkManager.ServerTime`.** `Time.time`을 타이머 기준으로 쓰지 않는다.
8. **씬 전환은 `NetworkManager.SceneManager.LoadScene()`만 사용.** `SceneManager.LoadScene()` 직접 호출 금지.
9. **로그는 공용 헬퍼를 쓴다.** `NetLog.Info(...)`가 `[Server]` / `[Client:2]` 접두어를 자동으로 붙인다. 창 두 개를 띄워 디버깅할 때 필수다.
10. **구독은 짝을 맞춘다.** `OnNetworkSpawn` ↔ `OnNetworkDespawn`, `OnEnable` ↔ `OnDisable`.
11. **UniTask에는 취소 토큰을 반드시 넘긴다.** 디스폰·씬 전환 뒤 살아남은 작업이 파괴된 객체를 건드리는 사고를 막는다.
    
    ```csharp
    await UniTask.Delay(1000, cancellationToken: destroyCancellationToken);
    ```
    
12. **비밀 정보는 `NetworkVariable`에 담지 않는다.** 제시어처럼 특정 플레이어만 알아야 하는 값은 **해당 클라이언트에게만 가는 RPC**로 보낸다. `NetworkVariable`은 모두에게 전송되므로 패킷을 보면 노출된다.
13. **PR 전 최소 2인 테스트(호스트 1 + 클라이언트 1)를 거친다.** 에디터 하나에서만 확인한 코드는 올리지 않는다. (Multiplayer Play Mode / ParrelSync / 빌드 실행)

## 7. 폴더 구조

```
Assets/Scripts/
├── Contract/   (GameContract.cs — 공용 enum·이벤트 정의. 합의 없이 수정 금지)
├── Network/    (NetworkConfig, NetLog, 연결·Relay·Lobby 관련)
├── Manager/    (GameDataManager, SingletonBase 등)
├── Data/       (GameData.*.cs, 순수 데이터 타입)
├── Object/     (순수 부품, 로직 모델)
├── Service/    (뷰모델 생성·보관, 네트워크 ↔ 뷰모델 중계)
├── ViewModel/  (ViewModelBase, ViewBase, 각 뷰모델)
└── UI/         (View 프리팹용 컴포넌트)
```

**[신규]** 기능(슬라이스)별로 하위 폴더를 나눠도 좋다. 예: `Network/Drawing/`, `Service/Drawing/`, `UI/Drawing/`

## 8. Git / 협업

### 브랜치 · PR

- **[변경] `main` + `feature/(기능)` 2단계.** (2인 규모에 `develop`은 과하다)
- `main` 직접 push 금지 → `feature/기능`에서 작업 후 PR
- 커밋 태그: `[feat]` `[fix]` `[chore]` `[refactor]`
- PR 제목: `[브랜치명(본인이름)] 기능 요약`, 작성 후 디스코드 공유
- **본인이 직접 머지 금지** (상대 코드를 읽게 만드는 장치이므로 반드시 유지)
- 본인 작업물 외 파일 수정 시 해당 작업자에게 요청

### [신규] 공유 자원 규칙

아래 세 가지는 충돌이 잦으므로 **수정 전 반드시 사전 공지**한다.

|대상|규칙|
|---|---|
|`GameContract.cs`|0주차에 같이 정하고, 변경 시 상대 동의 필수|
|씬 파일|한 번에 한 사람만. 매니저 오브젝트는 0주차에 미리 다 만들어 둔다|
|`Player.prefab`|붙일 컴포넌트를 0주차에 확정. 이후 추가 금지 (필요하면 씬 매니저 쪽 RPC로 처리)|

### [신규] Unity 프로젝트 설정 (첫 커밋 전 필수)

- Project Settings → Editor → **Asset Serialization: Force Text**
- Project Settings → Editor → **Version Control: Visible Meta Files**
- Unity용 `.gitignore` 적용 (`Library`, `Temp`, `Logs`, `obj` 제외)
- 이미지·사운드는 **Git LFS** 사용
- `.gitattributes`에 UnityYAMLMerge 설정
- **`.meta` 파일은 항상 함께 커밋** (누락 시 상대 프로젝트에서 참조가 끊어진다)

## 9. [신규] 작업 분배 규칙

- 기능(세로 슬라이스) 단위로 나눈다. 한 슬라이스는 **네트워크 코드 + 서비스 + UI를 모두 포함**한다.
- 각 슬라이스는 **자기만의 매니저 스크립트와 UI 프리팹**을 갖는다. 남의 파일을 수정하지 않는다.
- **코드 리뷰 필수** — 상대 승인 후 머지.
- **3주차에 슬라이스를 한 번 교환**해서 서로의 코드에 작은 기능을 추가해 본다.
- **30분 룰** — 30분 넘게 막히면 혼자 붙잡지 말고 상대를 부른다.
