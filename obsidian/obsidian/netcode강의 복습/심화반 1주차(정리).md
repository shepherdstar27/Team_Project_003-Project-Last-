## Unity Photon Fusion 멀티플레이 환경 정리

### 1. 멀티플레이의 기본 구조

멀티플레이는 **클라이언트, 네트워크, 서버** 세 가지로 이루어집니다.

|구성|역할|
|---|---|
|**클라이언트**|입력을 서버로 보내고, 서버에서 받은 상태를 화면에 그림(렌더링)|
|**서버**|판정(A가 B를 때렸는가?), 판정 결과를 모든 접속자에게 동기화, 모든 클라이언트 상태를 관리하고 검증|
|**네트워크**|서버와 클라이언트를 잇는 통로|

**[보충] 클라이언트 예측(Client-side Prediction)**  
클라이언트가 입력을 보내고 서버 응답만 기다리면 핑만큼 조작이 늦게 반응합니다. 그래서 Fusion(Host/Server 모드)의 클라이언트는 **서버 결과를 기다리지 않고 자기 입력의 결과를 미리 계산해서 보여줍니다.** 나중에 서버의 정답이 오면 그 값에 맞춰 보정합니다. 따라서 클라이언트는 "입력 + 렌더링"만 하는 게 아니라 "입력 + 예측 + 렌더링"을 한다고 보는 게 더 정확합니다.

**[보충] "입력 + 예측 + 렌더링" 기능중 예측은 퓨전만의 독특한 기능인지

퓨전이 만든 개념이 아닙니다. 1990년대 후반 **Quake(QuakeWorld)**에서 클라이언트 예측이 도입됐고, **Valve의 Source 엔진**(하프라이프, 카운터스트라이크)이 예측, 보간, 랙 보정 조합을 정리해서 업계 표준처럼 됐습니다.

**보간**은 거의 모든 도구가 기본으로 제공합니다.

**예측과 롤백**은 모든 도구에 있는 기능이 아닙니다. PUN2나 NGO에서는 개발자가 직접 구현해야 하는 경우가 많고, 이 구현이 네트워크 프로그래밍에서 가장 어려운 부분입니다.

퓨전의 차별점은 **틱 단위 상태 저장, 롤백, 재시뮬레이션을 엔진이 자동으로 해 준다**는 점입니다. 개발자는 `FixedUpdateNetwork()` 안에 로직을 쓰기만 하면 됩니다. 그 대가로 앞에서 말한 "같은 틱이 여러 번 실행될 수 있다" 같은 규칙을 지켜야 합니다.

입력 + 예측 + 렌더링"은 **실시간 액션 게임에서 서버 권한 구조를 쓰는 클라이언트**에 해당하는 설명입니다. 턴제, 카드 게임, 캐주얼 게임은 예측 없이 입력과 렌더링만으로도 충분




#### 핑 (Ping)

- 데이터가 클라이언트에서 서버까지 **왕복**하는 데 걸리는 시간(RTT, Round Trip Time)입니다.
- **[보충]** 한쪽 방향으로만 가는 시간은 **지연(Latency)**이라고 부르며, 대략 핑의 절반입니다.

#### 클라이언트끼리 직접 연결하면 되는데 왜 서버가 필요한가?

**[수정]** "교착상태(Deadlock)"는 서로가 서로를 기다리다 둘 다 멈추는 상황을 가리키는 운영체제/동시성 용어라서 여기에는 맞지 않습니다. 실제 이유는 다음과 같습니다.

1. **판정 충돌을 해결할 권한자(Authority)가 필요합니다.** A 화면에서는 맞았고 B 화면에서는 피했다면 누구 말이 맞을까요? 각자 보는 화면이 핑 때문에 조금씩 다르기 때문에, **"정답"을 정하는 단 하나의 기준(Single Source of Truth)**이 있어야 합니다.
2. **치팅을 막아야 합니다.** 클라이언트끼리 서로의 판정을 믿으면 조작한 쪽이 이깁니다.
3. **연결 수가 너무 많아집니다.** 전원이 서로 직접 연결하면 인원이 N명일 때 연결이 N×(N-1)/2개로 늘어납니다. 서버를 두면 N개로 충분합니다.
4. **NAT/방화벽 문제가 있습니다.** 가정용 공유기 환경에서는 클라이언트끼리 직접 연결이 안 되는 경우가 많습니다.



**[보충]**
### 연결 수가 많아지면 생기는 단점

예를 들어 8명이 서로 직접 연결하면 연결이 28개 생기고, 각 플레이어는 7명에게 따로 데이터를 보내야 합니다. 서버를 두면 각자 서버 하나에만 보내면 됩니다.

|단점|설명|
|---|---|
|**업로드 대역폭 폭증**|같은 내 위치 정보를 7명에게 7번 보내야 합니다. 가정용 인터넷은 다운로드보다 **업로드가 훨씬 느린 경우가 많아서** 여기서 먼저 막힙니다.|
|**CPU 부담 증가**|연결마다 패킷을 만들고 받고 확인해야 하므로 인원이 늘수록 처리량도 늘어납니다.|
|**연결 실패 확률 증가**|공유기(NAT)나 방화벽 때문에 직접 연결이 안 되는 경우가 있습니다. 연결 쌍이 28개면 그중 **하나라도 실패할 확률**이 크게 올라가고, 한 쌍이라도 끊기면 "A는 B가 보이는데 C는 B가 안 보이는" 상황이 생깁니다.|
|**가장 느린 사람에게 맞춰짐**|전원이 서로 연결돼 있으니 인터넷이 가장 나쁜 한 명이 전체 품질을 떨어뜨립니다.|
|**상태 불일치**|연결마다 도착 순서와 시간이 달라서 사람마다 보는 게임 상태가 어긋나기 쉽습니다. 정답을 정할 사람도 없습니다.|
|**IP 노출**|모든 플레이어가 서로의 IP를 알게 되므로 악의적인 사람이 다른 플레이어에게 DDoS 공격을 할 수 있습니다.|








### 2. 패킷과 보안

#### 패킷 (Packet)

- 네트워크로 주고받는 데이터의 단위입니다.

#### 후킹과 패킷 조작

- 패킷을 중간에 가로채 자기에게 유리하게 바꾸는 행위입니다.
- **[수정]** 용어를 조금 나누면 더 정확합니다.
    - **후킹(Hooking)**: 프로그램의 함수 호출이나 API를 가로채는 기법 전반을 말합니다. 패킷 조작에 쓰이는 수단 중 하나입니다.
    - **패킷 변조/조작**: 오가는 패킷 내용을 바꾸는 것 자체를 말합니다.
- **[보충]** 핵을 막는 핵심은 패킷 구조를 바꾸는 것보다 **"클라이언트를 믿지 않는 설계(Server Authoritative)"**입니다.
    - 클라이언트는 "위치 = (10, 5)" 같은 **결과**가 아니라 "앞으로 이동 키를 눌렀다" 같은 **입력**만 보냅니다.
    - 서버가 그 입력으로 직접 계산하므로, 패킷을 조작해도 서버가 말이 안 되는 값을 거부할 수 있습니다.
    - 암호화나 난독화는 보조 수단이고 근본적인 해결책은 아닙니다.

### 3. Photon Fusion을 쓰는 이유

- 패킷 송수신, 동기화, 예측 같은 멀티 환경을 직접 만들면 짧게 잡아도 수개월(6개월 이상)이 걸립니다.
- Photon Fusion이 이 부분을 대신 처리해 줍니다.
- **[수정] "무료"라는 표현:** 개발용 무료 플랜(동시 접속자 약 20 CCU)이 있어서 개발이나 개인 프로젝트는 무료로 할 수 있습니다. 하지만 **서비스 규모가 커지면 CCU(동시 접속자 수)에 따라 요금이 붙습니다.** 정확한 요금제는 Photon 공식 사이트에서 확인하세요.
- 다른 도구로는 Unity Netcode for GameObjects, Mirror, FishNet, Photon PUN2, Photon Quantum 등이 있습니다.
- **[수정]** "이름만 다를 뿐 사용법이 유사하다"는 **개념 수준에서만** 맞습니다. 네트워크 오브젝트, 권한(Authority), 동기화 변수, RPC 같은 개념은 공통이지만, **Fusion의 틱 기반 예측/롤백** 같은 핵심 구조는 도구마다 크게 다릅니다.



**[보충]**
### 공개 저장소에 올렸을 때 누가 동시 접속자를 늘리면 청구서가 오나?

**무료 플랜이라면 청구서는 오지 않습니다.** 다만 요금제에 따라 다릅니다.

|플랜|한도를 넘으면|
|---|---|
|**무료 플랜** (개발용 20 CCU 등)|**한도에서 막힙니다(Capped, 버스트 없음).** 초과한 접속은 거부되고 과금되지 않습니다.|
|**유료 월정액 플랜**|**버스트(Burst)가 허용됩니다.** 한도를 잠시 넘겨도 접속을 받아주고, **초과분은 다음 달 청구서에 자동으로 붙습니다.** 첫 초과 후 48시간 안에 업그레이드하지 않으면 Photon이 한도로 제한할 수 있습니다.|

그래서 **청구 위험은 유료 플랜을 쓸 때만** 생깁니다. 무료 플랜에서 최악의 경우는 누군가 접속자 자리를 다 차지해서 **내 게임에 정작 나와 친구들이 못 들어가는 것**(서비스 방해)입니다.


### 4. Photon Fusion의 3가지 모드

|모드|개념|장점|단점|적합한 게임|
|---|---|---|---|---|
|**Server**|전용(Dedicated) 서버가 게임을 판정|안정적이고 공정함, 누가 나가도 게임 유지|서버 운영비, 구현 난이도 높음|경쟁 FPS, 배틀로얄|
|**Host**|플레이어 한 명이 서버 역할을 겸함|서버 비용 없음|호스트 이탈·환경 문제, 호스트가 유리함|소규모 협동 게임|
|**Shared**|각 클라이언트가 자기 오브젝트에 대한 권한을 가짐|구현이 가장 쉬움|보안 취약, 공유 오브젝트 충돌|캐주얼, 소셜, 파티 게임|

#### Server 모드 [수정]

- "포톤에서 대여하는 서버"는 **정확하지 않습니다.** Server 모드에서는 **개발자가 Unity로 서버용 빌드(Headless)를 직접 만들어서** 자체 서버나 호스팅 업체(AWS, Edgegap 등)에 올립니다. Photon 클라우드는 매칭과 연결 중계 역할만 합니다.
- 그래서 비싼 이유는 Photon 요금이라기보다 **서버를 계속 켜 두는 호스팅 비용** 때문입니다.

#### Host 모드 [수정/보충]

- 무료라기보다는 **"전용 서버 비용이 들지 않는다"**가 정확합니다. Photon CCU 요금은 그대로 적용됩니다.
- 호스트는 핑이 0이라서 **판정에서 유리**합니다(Host Advantage).
- 호스트가 나가면 기본적으로 방이 끝나지만, Fusion은 **Host Migration**(다른 플레이어에게 호스트를 넘기는 기능)을 지원합니다. 다만 자동이 아니라 직접 구현해야 합니다.

#### Shared 모드 [수정]

- "모든 클라이언트가 서버처럼 기능한다"는 설명을 조금 고치면: **각 클라이언트가 자기가 소유한 오브젝트(State Authority)만 결정하고**, Photon 클라우드가 그 상태를 모아서 다른 클라이언트에게 전달합니다. 내 캐릭터는 내가 결정하고, 네 캐릭터는 네가 결정하는 방식입니다.
- **"초기 설정이 귀찮다"는 반대입니다.** Shared 모드는 세 모드 중 **설정과 구현이 가장 쉽습니다.** 오히려 Host/Server 모드가 예측과 롤백을 신경 써야 해서 더 어렵습니다.
- 실제 단점:
    - 각자 자기 결과를 보고하는 구조라서 **치팅에 취약**합니다.
    - 공과 문처럼 여러 명이 동시에 건드리는 **공유 오브젝트는 권한 충돌**이 생기므로 권한 이전(Request State Authority) 처리가 필요합니다.
    - 예측/롤백이 없어서 **정밀한 경쟁 게임에는 부적합**합니다.

### 5. NetworkRunner

**[수정]** "컴포넌트 자체가 하나의 게임 방"보다는 **"이 클라이언트가 세션(방)에 참여하는 창구이자 엔진"**이 더 정확합니다.

- 방(Session)은 Photon 클라우드나 서버에 있고, **각 클라이언트가 자기 NetworkRunner를 하나씩** 가집니다.
- 에디터에서는 한 프로세스 안에 Runner를 여러 개 띄워 멀티 테스트를 할 수도 있습니다(Multi-Peer 모드).

#### NetworkRunner의 기능

|기능|설명|관련 API 예시|
|---|---|---|
|**세션 통제**|게임 시작/종료, 모드 선택|`StartGame(new StartGameArgs { GameMode = ... })`, `Shutdown()`|
|**틱 관리**|고정 간격으로 입력 수집 → 시뮬레이션 → 동기화|`FixedUpdateNetwork()`, `Runner.Tick`|
|**플레이어 관리**|누가 들어오고 나갔는지|`OnPlayerJoined(PlayerRef)`, `OnPlayerLeft`, `Runner.ActivePlayers`|
|**네트워크 오브젝트 관리**|캐릭터, 아이템 등을 네트워크 오브젝트로 생성/삭제|`Runner.Spawn()`, `Runner.Despawn()`|
|**[보충] 씬 관리**|모든 클라이언트가 같은 씬을 로드하도록 동기화|`Runner.LoadScene()`|

**[보충] 네트워크 오브젝트 주의점**

- 네트워크 오브젝트는 `NetworkObject` 컴포넌트가 붙은 프리팹이어야 합니다.
- **`Instantiate()`가 아니라 반드시 `Runner.Spawn()`으로 생성**해야 다른 클라이언트에게도 나타납니다.
- 동기화할 변수에는 `[Networked]` 속성을 붙입니다.

### 6. 틱(Tick) 개념 [보충]

#### 틱이란?

**게임 상태를 계산하는 "고정된 시간 간격 한 칸"**입니다.

- 예를 들어 Tick Rate가 60이면 1초에 60번, 즉 **약 16.67ms마다 1틱**입니다(Fusion 기본값은 60이고 프로젝트 설정에서 바꿀 수 있습니다).
- 매 틱마다 **입력 수집 → 게임 상태 시뮬레이션 → 결과 전파**가 일어나는데, 이것을 네트워크 루프라고 합니다. 이 부분은 제대로 이해하신 겁니다.

#### [수정] 틱 ≠ 프레임

노트에 "매틱(매 프레임)"이라고 쓰셨는데, **틱과 프레임은 서로 다른 것**이고 이 차이가 핵심입니다.

| 항목           | 프레임 (Frame)                       | 틱 (Tick)               |
| ------------ | --------------------------------- | ---------------------- |
| 간격           | **가변** (PC 성능에 따라 30fps, 144fps…) | **고정** (예: 60Hz)       |
| 목적           | 화면 그리기                            | 게임 로직 계산               |
| Fusion 함수    | `Render()`                        | `FixedUpdateNetwork()` |
| 비슷한 Unity 개념 | `Update()`                        | `FixedUpdate()`        |

#### 왜 프레임이 아니라 틱을 써야 할까?

- A의 PC는 144fps, B의 PC는 30fps라고 해 보겠습니다. 프레임마다 이동 계산을 하면 **두 사람의 계산 횟수가 달라져 결과가 어긋납니다.**
- 틱은 모두에게 똑같은 간격이므로 **"37번째 틱에 A가 점프 키를 눌렀다"처럼 모두가 같은 시점을 기준으로 이야기할 수 있습니다.** 온라인 게임에서는 틱 번호가 일종의 공용 시계 역할을 합니다.
- 게임 로직은 `FixedUpdateNetwork()`에 쓰고 `Runner.DeltaTime`(고정값)을 사용합니다. 시각 효과나 보간은 `Render()`에서 처리합니다.

#### 한 틱 동안 일어나는 일 (Host/Server 모드)

```
[클라이언트]                                [서버/호스트]
1. OnInput()에서 입력 수집
   (키보드 → INetworkInput 구조체)
2. 입력을 서버로 전송  ───────────────→  3. 모든 플레이어 입력으로
   + 서버 결과를 기다리지 않고                  틱 N 시뮬레이션 (정답)
     내 화면에서 먼저 예측 실행               4. 결과 상태를 전원에게 전송
5. 서버의 틱 N 정답 도착  ←───────────────
6. 내 예측과 다르면 → 틱 N으로 되돌리고(롤백)
   현재 틱까지 다시 계산(재시뮬레이션)
```

#### 예측과 롤백 (Prediction & Rollback)

- 핑 때문에 서버의 정답은 항상 **과거 틱**에 대한 것입니다. 클라이언트는 그동안 앞서서 예측하고 있습니다.
- 정답이 도착하면 그 틱으로 되돌아간 뒤 현재까지 **다시 계산**합니다. 대부분 예측이 맞기 때문에 플레이어는 거의 느끼지 못합니다.
- **실무 주의점:** 재계산 때문에 **`FixedUpdateNetwork()`가 같은 틱에 여러 번 호출될 수 있습니다.** 그래서 사운드나 이펙트 재생처럼 한 번만 일어나야 하는 일을 여기에 그냥 쓰면 여러 번 재생됩니다. `Runner.IsForward`(처음 계산하는 틱인지 여부)로 확인하거나 `Render()`에서 처리해야 합니다.
- Shared 모드에는 롤백이 없습니다. 각자 자기 오브젝트를 계산하고, 남의 오브젝트는 받은 값을 보간해서 보여줍니다.

#### 틱과 렌더링 사이: 보간 (Interpolation)

- 틱이 60Hz이고 모니터가 144Hz라면 틱과 틱 사이에 프레임이 여러 장 있습니다.
- 틱 값만 그대로 그리면 화면이 뚝뚝 끊겨 보이기 때문에, Fusion은 **두 틱 사이를 부드럽게 이어서(보간)** 렌더링합니다.

한 줄 요약: **NetworkRunner가 고정 간격(틱)마다 입력을 모아 시뮬레이션하고, 서버(또는 권한자)가 정답을 정해 모두에게 동기화하며, 클라이언트는 예측으로 지연을 숨기고 보간으로 화면을 부드럽게 만든다.**
