# DB 정리 노트 (파일 시스템 → DBMS → 게임 실무)


---

## 0. 큰 그림 — 왜 "데이터 드리븐 / 세이브·로드 / MVVM"이 DB와 한 묶음인가

메모 첫 줄의 직관은 맞습니다. 세 개를 잇는 공통 주제는 하나입니다.

> **"로직(코드)과 데이터를 분리한다."**

|개념|분리하는 대상|DB와의 연결 고리|
|---|---|---|
|데이터 드리븐 설계|밸런스·스펙 데이터 ↔ 코드|데이터가 바뀌어도 코드를 안 고치게 = **데이터 독립성**|
|세이브 / 로드|런타임 메모리 상태 ↔ 영속 저장소|**영속성(Persistence)**, DB의 D(Durability)|
|MVVM|View ↔ Model(데이터)|Model이 곧 데이터 소스(파일/DB/서버) 계층|

> **🔧 정정 — MVVM은 DB 기술이 아닙니다.** MVVM은 **UI 아키텍처 패턴**입니다. DB와 "관련되어 있다"는 건, MVVM의 Model 계층이 영속 데이터(파일/DB/서버 응답)를 담당하고, ViewModel이 그것을 View가 쓰기 좋은 형태로 가공한다는 의미에서입니다. 즉 **DB → Repository → Model → ViewModel → View** 라는 데이터 흐름의 양쪽 끝에 DB와 UI가 있는 구조입니다. "DB의 일부"가 아니라 "DB를 소비하는 쪽의 설계"입니다.

## 1. DB 이전 — 파일 시스템 시대

각 응용 프로그램이 자기만의 파일을 만들어 직접 읽고 씁니다.

```
인사관리 프로그램 ──> 인사.dat
급여 프로그램     ──> 급여.dat     ← 같은 사람의 주소가 양쪽에 따로 존재
```

메모의 예시가 정확히 이 문제입니다.

```
001슬라임30
   ↓ 컬럼(속성) 하나 추가
001fire슬라임30
```

파싱 코드가 "0~2번째 글자 = ID, 3번째부터 = 이름, 뒤 2자리 = 레벨" 식으로 **오프셋을 하드코딩**하고 있으니, 데이터 포맷이 바뀌면 이 파일을 읽는 **모든 프로그램의 코드를 고쳐야** 합니다. 이것이 **데이터 종속성(Data Dependency)** 입니다.

### 🔧 정정 1 — 연대

메모에는 "1960~1980년대"로 되어 있는데, 구분하면 이렇습니다.

|시기|사건|
|---|---|
|1950s ~ 1960s 초|순수 **파일 시스템** 시대 (마그네틱 테이프, 순차 접근)|
|1968|IBM **IMS** — 계층형(Hierarchical) DBMS|
|1969~71|**CODASYL DBTG** — 네트워크형 DBMS|
|**1970**|**E. F. Codd**, 관계형 모델 논문 발표 (IBM 연구원)|
|1974~79|IBM **System R** (SQL의 원형 SEQUEL 탄생)|
|**1979**|**Oracle V2** — 최초의 상용 RDBMS|
|1983|IBM **DB2** (뒤늦게 출시)|
|1980s~|RDBMS가 업계 표준으로 정착|

즉 "파일 시스템 → DB"의 전환점은 **1970년(관계형 모델)** 과 **1979년(Oracle 상용화)** 입니다. 그리고 파일 시스템 이후 바로 관계형이 나온 게 아니라, **계층형 → 네트워크형 → 관계형** 순서로 발전했습니다. (면접에서 자주 묻습니다.)

### 🔧 정정 2 — "파일 저장은 I/O라서 느리다"는 설명은 부정확합니다

> 메모: _"레벨업, 경험치 등 정보가 단편적으로 자주 바뀌는데, 이는 I/O로 굉장히 느리고 무거운 작업"_

**DB도 결국 디스크에 I/O를 합니다.** DB가 파일 직접 쓰기보다 유리한 이유는 I/O를 없애서가 아니라, **I/O를 영리하게 다루기 때문**입니다.

|DB의 기법|내용|
|---|---|
|**버퍼 풀(Buffer Pool)**|자주 쓰는 페이지를 메모리에 캐싱, 디스크 접근 최소화|
|**WAL (Write-Ahead Logging)**|변경을 먼저 **로그에 순차 쓰기**로 기록 → 랜덤 쓰기보다 훨씬 빠름|
|**인덱스(B+Tree)**|전체 스캔 없이 O(log n)으로 원하는 레코드만 탐색|
|**부분 갱신**|경험치 1 오르면 그 컬럼만 UPDATE. 파일은 보통 **전체를 다시 씀**|
|**그룹 커밋**|여러 트랜잭션의 fsync를 묶어서 한 번에|

그래서 파일 시스템의 **진짜** 문제는 "느리다"가 아니라 이 세 가지입니다.

1. **부분 갱신이 어렵다** — 경험치 1 바뀌어도 세이브 파일 전체를 직렬화해서 다시 씀
2. **원자성이 없다** — 쓰다가 전원이 꺼지면 세이브 파일이 **깨짐**(반쯤 쓰인 파일). DB는 트랜잭션으로 "전부 아니면 전무"를 보장
3. **동시성 제어가 없다** — 두 프로세스가 같은 파일을 동시에 쓰면 덮어씀. 락 관리를 직접 해야 함

> ➕ **보충 — 파일 저장이 나쁜 게 아닙니다.** 오늘날 **싱글플레이 게임의 로컬 세이브는 여전히 파일(JSON/바이너리/SQLite)** 로 하는 게 정석입니다. 파일 시스템의 한계가 문제가 되는 건 **여러 프로그램·여러 사용자가 같은 데이터를 공유할 때**입니다. 그래서 온라인 게임은 서버 DB를 씁니다. 즉 "파일 vs DB"는 우열이 아니라 **공유·동시성·무결성 요구 수준의 문제**입니다.

## 2. 파일 시스템의 6가지 한계 (메모 정리 + 보정)

|한계|내용|정확한 표현|
|---|---|---|
|**데이터 종속성**|데이터의 물리적 구조가 프로그램 코드에 하드코딩|포맷 변경 → 코드 변경 (유지보수성 저하)|
|**데이터 중복성**|프로그램마다 파일을 따로 만들어 같은 내용 중복|저장 공간 낭비 + 갱신 비용 증가|
|**데이터 불일치 (Inconsistency)**|인사관리에서 주소를 바꿨는데 급여 쪽은 그대로|중복의 **결과**. 중복이 원인, 불일치가 증상|
|**데이터 무결성 침해**|의도와 다른 형식·범위의 값이 들어감|제약조건(Constraint)을 강제할 주체가 없음|
|**표준화·호환성 부재**|같은 "날짜"를 각자 다른 자료형으로|데이터 표준 정의/공유 불가|
|**보안성 결여**|—|🔧 아래 참고|

> **🔧 정정 — 보안 항목** 메모에는 _"DB는 각 테이블에 대한 접근권한 다름"_ 이라고 DB 쪽 장점만 적혀 있습니다. 파일 시스템의 문제로 표현하면 이렇습니다. 파일 시스템에도 OS 수준 권한(읽기/쓰기/실행)은 있지만, **파일 단위**가 최소 단위입니다. "이 사용자는 사원 테이블에서 이름은 볼 수 있지만 연봉 컬럼은 볼 수 없다" 같은 **레코드·컬럼 단위의 세밀한 통제가 불가능**합니다. DBMS는 `GRANT/REVOKE`와 **뷰(View)** 로 이걸 해결합니다.

> ➕ **보충 — 무결성의 4가지 종류** (면접 빈출)
> 
> - **개체 무결성(Entity)** — PK는 NULL도, 중복도 안 됨
> - **참조 무결성(Referential)** — FK는 참조하는 테이블에 실제 존재하는 값이어야 함
> - **도메인 무결성(Domain)** — 자료형·범위·NOT NULL·CHECK 제약
> - **사용자 정의 무결성** — 업무 규칙 (예: "레벨은 1~100")

## 3. DBMS — 응용프로그램과 데이터 사이의 중재자

메모의 구조도가 맞습니다.

```
각 응용프로그램  <->  DBMS  <->  OS  <->  데이터베이스(디스크)
```

> **🔧 정정 (사소하지만 정확히)** 대부분의 DBMS는 OS의 파일 시스템 위에 데이터 파일을 두지만, Oracle 등 일부는 성능을 위해 **파일 시스템을 우회(Raw Device / ASM)** 하기도 합니다. 그래서 "반드시 OS를 거친다"보다는 **"DBMS가 저장 계층을 캡슐화한다"** 가 정확합니다. 실무 관점의 전체 경로: `앱 코드 → ORM/드라이버(JDBC·ADO.NET) → 네트워크 → DBMS(파서→옵티마이저→실행기→버퍼풀) → 스토리지`

### DBMS가 하는 일

메모의 _"조회, 추가, 제거, 삭제, 변경"_ → **제거와 삭제가 중복**입니다. 정리하면:

|CRUD|SQL (DML)|
|---|---|
|**C**reate|`INSERT`|
|**R**ead|`SELECT`|
|**U**pdate|`UPDATE`|
|**D**elete|`DELETE`|

> ➕ **보충 — SQL의 분류** (면접 빈출)
> 
> - **DDL** (정의): `CREATE`, `ALTER`, `DROP`, `TRUNCATE`
> - **DML** (조작): `SELECT`, `INSERT`, `UPDATE`, `DELETE`
> - **DCL** (제어): `GRANT`, `REVOKE`
> - **TCL** (트랜잭션): `COMMIT`, `ROLLBACK`, `SAVEPOINT`

### DBMS를 두어 얻는 것 (메모 그대로 + 정리)

- **중앙 집중 관리** — DB 접근은 DBMS를 통해서만
- **데이터 독립성** — 저장 구조가 바뀌어도 응용프로그램은 그대로
- **무결성 보장** — 제약조건을 DBMS가 강제
- **보안성** — 사용자/역할별 권한
- ➕ **동시성 제어** — 여러 사용자가 동시에 접근해도 일관성 유지 (락, MVCC)
- ➕ **장애 복구** — 로그 기반 Redo/Undo로 장애 시점 복원

### ➕ 보충 — 3단계 스키마 (ANSI/SPARC), 데이터 독립성의 정확한 정의

메모의 "데이터 독립성"을 제대로 설명하는 구조입니다.

|단계|스키마|관점|
|---|---|---|
|외부|**External Schema**|각 사용자·앱이 보는 뷰 (여러 개)|
|개념|**Conceptual Schema**|조직 전체의 통합된 논리 구조 (테이블, 관계, 제약)|
|내부|**Internal Schema**|실제 물리적 저장 구조 (파일, 인덱스, 페이지)|

- **논리적 독립성** = 개념 스키마가 바뀌어도(컬럼 추가 등) 외부 스키마/앱은 영향 없음
- **물리적 독립성** = 내부 스키마가 바뀌어도(인덱스 추가, 디스크 교체) 개념 스키마/앱은 영향 없음

👉 **메모의 `001슬라임30 → 001fire슬라임30` 문제가 바로 "논리적 독립성이 없었다"는 뜻입니다.** RDB에서는 `ALTER TABLE ADD COLUMN element`만 하면 기존 쿼리는 그대로 동작합니다.

## 4. 🔧 가장 중요한 정정 — "관계(Relation)"의 의미

> 메모: _"관계중심 이라는 용어가 중요."_

맞습니다. 그런데 **거의 모든 사람이 여기서 오해합니다.**

> **관계형 DB의 "관계(Relation)"는 "테이블 간의 연결 관계"가 아닙니다.**

- **Relation** = 집합론·수학에서의 _관계_, 즉 **튜플(행)의 집합** = **테이블 그 자체**
- **Relationship** = 테이블 사이의 연관(1:1, 1:N, N:M) — FK로 표현하는 것

즉 "관계형 데이터베이스"는 **"데이터를 릴레이션(테이블)이라는 수학적 구조로 표현하고, 그 위에서 관계 대수(Relational Algebra) 연산을 한다"** 는 뜻입니다. FK로 테이블을 잇는다는 의미가 아닙니다.

### ➕ 보충 — 용어 대응표 (면접에서 물어봅니다)

|관계 모델 용어|실제 DB 용어|
|---|---|
|Relation|테이블|
|Tuple|행(Row), 레코드|
|Attribute|열(Column), 필드|
|Degree(차수)|컬럼의 개수|
|Cardinality(카디널리티)|행의 개수|
|Domain|컬럼이 가질 수 있는 값의 범위(자료형)|

### ➕ 보충 — 정규화(Normalization)

메모에 빠져 있는데, **중복 제거**가 RDB의 핵심 무기입니다.

- **목표**: 데이터 중복 제거 → 갱신 이상(Anomaly) 방지
- **1NF** 모든 속성이 원자값 / **2NF** 부분 함수 종속 제거 / **3NF** 이행 함수 종속 제거 / **BCNF** 모든 결정자가 후보키
- **갱신 이상 3종**: 삽입 이상, 갱신 이상, 삭제 이상
- ⚠️ 실무에서는 조인 비용 때문에 **일부러 역정규화(Denormalization)** 해서 읽기 성능을 얻습니다. 게임 서버에서 흔합니다.

## 5. 역사 — IBM은 왜 주저했고 Oracle은 어떻게 장악했나

메모 내용이 사실입니다. 정확히 붙이면:

- **Codd(IBM 연구원)** 가 1970년 관계형 모델 논문 발표
- IBM은 **System R** 로 프로토타입까지 만들고 **SQL(SEQUEL)** 도 IBM에서 나옴
- 그런데 IBM은 이미 **IMS(계층형)** 로 큰 매출을 올리고 있었고, "SQL은 느리다"는 내부 회의론도 있어 상용화를 미룸 → **전형적인 innovator's dilemma**
- **Larry Ellison** 이 Codd의 논문과 System R 자료를 보고 1977년 창업(Software Development Laboratories), **1979년 Oracle V2** 를 먼저 출시
- IBM은 **1983년 DB2** 로 뒤늦게 진입

메모대로 Oracle은 글로벌 **금융권**에서 대규모 데이터 처리 성능·복구 능력·보안성을 검증받아 신뢰를 얻었고, 그것이 곧 엔터프라이즈 시장 장악으로 이어졌습니다.

## 6. 주요 DBMS 비교 (메모 + 게임 개발자라면 반드시 알아야 할 것들 추가)

|제품|라이선스|주 사용처|메모의 자동차 비유|
|---|---|---|---|
|**Oracle**|상용 (매우 고가)|금융, 대기업, 통신사|방탄 리무진 ✅|
|**SQL Server**|상용|MS 생태계(.NET, Windows 서버)|잘 갖춰진 대형 세단 ✅|
|**MySQL / MariaDB**|오픈소스(듀얼)|웹, 스타트업, **게임 서버 1순위**|튜닝하기 좋은 차 ✅|
|➕ **PostgreSQL**|완전 오픈소스|표준 준수·기능 풍부, 최근 대세|성능 좋은 오픈소스 정비 매뉴얼 완비 차|
|➕ **SQLite**|퍼블릭 도메인|**게임 클라이언트 로컬 세이브/마스터 데이터**|서버 없는 단일 파일 DB, 자전거|
|➕ **Redis**|오픈소스 (NoSQL)|랭킹, 세션, 매치메이킹, 캐시|인메모리 — 초경량 레이싱 카트|

> **🔧 정정 — MySQL은 지금 Oracle 소유입니다.** 2008년 Sun이 MySQL AB를 인수하고, 2010년 Oracle이 Sun을 인수하면서 **MySQL의 소유권은 Oracle에 있습니다.** 그래서 원 개발자들이 포크한 **MariaDB** 가 나왔고, 요즘 오픈소스 진영은 **PostgreSQL** 쪽으로 많이 이동했습니다.

> ➕ **보충 — 현재 흐름** 온프레미스 Oracle → **클라우드 매니지드 DB**(AWS RDS/Aurora, Google Cloud SQL, Azure SQL)로 이동하는 추세입니다. 라이선스 비용과 운영 부담 때문입니다.

## 7. RDB vs NoSQL

### 메모 내용 확인

|항목|메모|판정|
|---|---|---|
|게임은 일반적으로 RDB|✅|맞지만 **하이브리드**가 실제 (9장)|
|정형 데이터, 엄격한 스키마|✅|맞음|
|NoSQL은 SNS·비정형·수평 확장|✅|맞음|
|NoSQL은 고정 스키마 없음|⚠️|뉘앙스 정정 필요|
|NoSQL은 거대한 맵(키-밸류)|⚠️|한 종류만 설명함|
|RDB는 대용량 들어오면 다운타임|⚠️|인과관계 정정 필요|

### 🔧 정정 1 — "대용량 데이터가 들어와서 다운타임"이 아닙니다

> 메모: _"대용량의 데이터가 계속 들어오면 스키마에 맞춰 변경해 넣기 위한 긴 시간의 다운타임 발생"_

다운타임이 생기는 건 **데이터가 들어올 때가 아니라 스키마를 바꿀 때(`ALTER TABLE`)** 입니다. 그리고 **테이블에 이미 쌓인 데이터가 많을 때** 그 ALTER가 오래 걸립니다. 순서를 정리하면:

> 데이터가 이미 수억 건 쌓여 있음 → 기획이 컬럼 추가를 요구 → `ALTER TABLE` 이 테이블 전체를 재구성 + 락 → **서비스 점검(다운타임)**

또한 현대 RDBMS는 **Online DDL**(MySQL 5.6+), `pt-online-schema-change`, `gh-ost` 같은 무중단 스키마 변경 도구로 이걸 상당히 완화했습니다. "RDB는 스키마 변경이 불가능하다"가 아니라 **"비싸다"** 가 정확합니다.

### 🔧 정정 2 — RDB의 진짜 확장 한계는 "수평 확장"입니다

메모에 "NoSQL의 장점은 확장성"이라고만 되어 있는데, 그 반대편을 정확히 알아야 합니다.

| |수직 확장 (Scale-Up)|수평 확장 (Scale-Out)|
|---|---|---|
|방식|서버 한 대의 CPU/RAM/디스크 증설|서버 대수를 늘림|
|RDB|✅ 이걸 주로 함|❌ 어려움|
|NoSQL|가능|✅ 이걸 전제로 설계됨|

**RDB가 수평 확장이 어려운 이유**: JOIN과 트랜잭션이 **여러 노드에 걸치면** 비용이 폭발합니다(분산 트랜잭션, 2PC). 그래서 RDB는 **샤딩(Sharding)** 을 하는데, 이건 애플리케이션이 "이 유저는 몇 번 샤드"를 알아야 하고 샤드 간 JOIN은 포기해야 합니다. 게임에서 흔히 보는 **"서버 1채널 / 2채널"** 구조가 사실상 샤딩입니다.

### 🔧 정정 3 — NoSQL은 "스키마가 없는" 게 아닙니다

정확히는 **Schema-on-Read** 입니다.

- RDB = **Schema-on-Write**: 쓸 때 DBMS가 스키마를 검증 → 잘못된 데이터는 못 들어옴
- NoSQL = **Schema-on-Read**: 일단 넣고, 읽을 때 애플리케이션이 해석

즉 **스키마가 사라진 게 아니라, 검증 책임이 DBMS에서 애플리케이션 코드로 옮겨간 것**입니다. 그래서 유연하지만, 옛 버전/새 버전 문서가 섞이면 코드가 모든 버전을 처리해야 하는 부담이 생깁니다.

### ➕ 보충 — NoSQL은 4가지 유형입니다

메모의 "거대한 맵으로 키-밸류"는 이 중 첫 번째입니다.

|유형|대표 제품|구조|게임에서의 용도|
|---|---|---|---|
|**Key-Value**|Redis, DynamoDB|key → value|세션, 캐시, 랭킹(Sorted Set)|
|**Document**|MongoDB, Couchbase|key → JSON 문서|유저 프로필, 인벤토리 스냅샷|
|**Column-Family**|Cassandra, HBase|행 키 + 컬럼 패밀리|대량 로그, 시계열 지표|
|**Graph**|Neo4j|노드 + 엣지|친구 관계, 추천|

### ➕ 보충 — ACID vs BASE, 그리고 CAP 정리

이게 RDB/NoSQL 선택의 이론적 근거입니다.

- **CAP 정리**: 분산 시스템은 **Consistency(일관성) / Availability(가용성) / Partition tolerance(분할 내성)** 중 **최대 2개만** 만족. 네트워크 분할은 현실에서 피할 수 없으므로 실질적으로 **C냐 A냐**의 선택.
    - RDB 계열 = **CP** (일관성 우선, 확실하지 않으면 에러를 냄)
    - 다수의 NoSQL = **AP** (일단 응답, 나중에 수렴)
- **BASE** (NoSQL의 철학): **B**asically **A**vailable, **S**oft state, **E**ventually consistent — **결과적 일관성**

👉 게임에서 **재화·결제·아이템**은 결과적 일관성이 절대 허용되지 않습니다(아이템 복사 버그). 그래서 RDB입니다. 👉 반대로 **"친구 수" 표시가 3초 늦게 갱신되는 것**은 아무도 안 죽습니다. 그래서 SNS는 NoSQL로 괜찮습니다.

## 8. 트랜잭션 — 메모의 "(트랜잭션?)" 에 대한 답

> **트랜잭션 = 쪼갤 수 없는 하나의 논리적 작업 단위. 전부 성공하거나, 전부 없던 일이 된다.**

### 게임으로 보는 예시 — 아이템 거래

```
BEGIN TRANSACTION
  A의 인벤토리에서 '전설의 검' 삭제
  B의 인벤토리에 '전설의 검' 추가
  A의 골드 += 1000
  B의 골드 -= 1000
COMMIT
```

이 중간에 서버가 죽으면?

- **트랜잭션 없음** → 검은 A에서 사라졌는데 B에게 안 갔음 = **아이템 소멸** (또는 반대로 **아이템 복사**)
- **트랜잭션 있음** → 자동 `ROLLBACK`. 아무 일도 없었던 상태로 복귀

**이것이 게임이 RDB를 쓰는 가장 결정적인 이유입니다.** 메모에 "트랜잭션이 빈번함"이라고 적은 게 정확한 포인트였습니다.

### ACID (면접 필수)

|속성|의미|구현 수단|
|---|---|---|
|**A**tomicity (원자성)|전부 아니면 전무|Undo 로그, Rollback|
|**C**onsistency (일관성)|트랜잭션 전후로 제약조건이 항상 만족|제약조건(PK/FK/CHECK), 트리거|
|**I**solation (격리성)|동시 실행 트랜잭션이 서로 간섭하지 않음|락(Lock), MVCC|
|**D**urability (지속성)|커밋된 건 장애가 나도 남아 있음|WAL(로그 선행 기록), fsync|

### ➕ 보충 — 격리 수준(Isolation Level)과 이상 현상

|격리 수준|Dirty Read|Non-Repeatable Read|Phantom Read|
|---|---|---|---|
|READ UNCOMMITTED|발생|발생|발생|
|READ COMMITTED|차단|발생|발생|
|REPEATABLE READ|차단|차단|발생(MySQL은 대부분 차단)|
|SERIALIZABLE|차단|차단|차단|

- **Dirty Read**: 커밋 안 된 값을 읽음
- **Non-Repeatable Read**: 같은 행을 두 번 읽었는데 값이 다름
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 행 개수가 다름

기본값: MySQL(InnoDB) = **REPEATABLE READ**, PostgreSQL/Oracle/SQL Server = **READ COMMITTED**. 격리 수준을 높이면 안전하지만 락 경합이 늘어 **동시 처리량이 떨어집니다.** 게임 서버는 보통 READ COMMITTED + 필요한 곳에만 명시적 락(`SELECT ... FOR UPDATE`)을 씁니다.

> ➕ **데드락(Deadlock) 주의**: A가 1번 행 락 후 2번을 기다리고, B가 2번 락 후 1번을 기다리면 영구 대기. 해결의 정석은 **항상 같은 순서로 락을 잡기**(예: 거래 시 유저 ID가 작은 쪽부터).

## 9. 게임에서의 실제 데이터 구조 — 하이브리드

> **🔧 정정 — "게임은 RDB" 는 절반만 맞습니다. 실무는 여러 저장소를 용도별로 섞습니다.**

### 9-1. 게임 데이터는 성격이 완전히 다른 두 종류입니다

| |**마스터 데이터 (기획 데이터)**|**유저 데이터 (세이브 데이터)**|
|---|---|---|
|내용|몬스터 스펙, 아이템 테이블, 스킬 계수, 밸런스|레벨, 경험치, 인벤토리, 재화, 퀘스트 진행|
|변경 시점|**빌드/패치 시점에만**|**플레이 중 실시간**|
|권한|**읽기 전용**|읽기/쓰기|
|저장 위치|Excel → CSV/JSON/바이너리/SQLite 로 **클라이언트에 배포**|**서버 RDB** (온라인) / 로컬 파일 (싱글)|
|누가 만듦|기획자 (Excel)|런타임|

👉 **메모의 `001슬라임30` 예시는 마스터 데이터입니다.** 그리고 이 부분이 바로 **데이터 드리븐 설계**가 적용되는 영역입니다. 기획자가 Excel에서 슬라임의 HP를 30→35로 바꾸고 빌드만 돌리면, 프로그래머는 코드를 한 줄도 안 고칩니다. 이게 메모 첫 줄의 "데이터 드리븐"입니다.

👉 반대로 **유저 데이터**가 트랜잭션·무결성이 필요한 영역이고, 여기가 **DB**의 영역입니다.

### 9-2. 실무 구성 예시 (모바일/온라인 게임 서버)

|저장소|담는 것|이유|
|---|---|---|
|**RDB** (MySQL/PostgreSQL)|계정, 결제, 재화, 인벤토리, 우편|트랜잭션·무결성이 생명|
|**Redis** (인메모리 KV)|세션 토큰, 랭킹(Sorted Set), 매치메이킹 큐, 분산 락, 캐시|초저지연. 날아가도 재구성 가능한 데이터|
|**NoSQL / 데이터 웨어하우스** (BigQuery, S3+Athena, Cassandra)|플레이 로그, 이탈 분석, A/B 테스트 지표|쓰기 폭주 + 스키마 유연 + 분석용|
|**파일 / SQLite** (클라이언트)|마스터 데이터, 옵션, 싱글플레이 세이브|서버 불필요, 배포 간편|

> ➕ **자주 쓰는 패턴**: 인벤토리를 매 조작마다 RDB에 쓰면 부하가 큽니다. 그래서 **Redis에 유저 상태를 올려두고(write-back), 일정 주기 또는 로그아웃 시점에 RDB로 flush** 합니다. 단, **결제와 유료 재화는 예외 없이 즉시 RDB 트랜잭션**으로 처리합니다.

### 9-3. 세이브/로드 설계 시 꼭 챙길 것

1. **원자적 쓰기** — 로컬 세이브는 `임시 파일에 쓰기 → fsync → rename`. rename은 원자적이라 세이브 파일이 깨지지 않습니다. (DB의 A와 D를 손으로 구현하는 것)
2. **버전 필드** — 세이브 데이터에 `version` 을 넣고 마이그레이션 코드를 둡니다. 패치로 필드가 바뀌면 구 세이브를 변환해야 하니까요. **이것이 RDB의 스키마 마이그레이션과 같은 문제입니다.**
3. **멱등성(Idempotency)** — 결제 완료 요청이 네트워크 재시도로 두 번 오면? 요청마다 고유 ID를 붙이고 이미 처리한 ID는 무시합니다. (재화 두 번 지급 방지)
4. **직렬화 포맷** — JSON(디버깅 쉬움) vs MessagePack/Protobuf/FlatBuffers(작고 빠름). 치트 방지를 위해 로컬 세이브는 암호화/해시 서명.

## 10. 🔧 정정 — 블록체인은 "DBMS의 반대 개념"이 아닙니다

> 메모: _"위 DBMS와 반대 되는 개념이 블록체인 등장"_

비교하고 싶은 축은 **"중앙 집중 vs 탈중앙(분산 신뢰)"** 입니다. 그런데 **DBMS에도 분산 DB가 있으므로**(Cassandra, CockroachDB, Oracle RAC) "DBMS의 반대 = 블록체인"은 성립하지 않습니다. 정확히는:

| |RDBMS|블록체인|
|---|---|---|
|신뢰 주체|**중앙 관리자(DBA)를 신뢰**|**신뢰할 주체가 없다고 가정**, 합의 알고리즘으로 대체|
|데이터 변경|UPDATE / DELETE 자유|**Append-only**, 사실상 수정·삭제 불가|
|처리량|수만~수십만 TPS|수~수천 TPS|
|참여자|조직 내부|익명의 다수|

즉 블록체인은 **"참여자끼리 서로를 못 믿는 환경에서 원장을 공유하려면?"** 이라는 다른 문제를 푸는 기술입니다. 성능·비용 때문에 게임의 유저 데이터 저장소로는 부적합하고, 실제 게임 적용은 아이템 소유권 증명(NFT) 같은 제한적 영역입니다.

> 면접에서는 "블록체인은 DBMS의 대체가 아니라, **신뢰 모델이 다른 특수한 분산 원장**이며, 갱신 불가·낮은 처리량이라는 트레이드오프를 대가로 탈중앙 검증 가능성을 얻은 것"이라고 답하면 충분합니다.

## 11. 다시 처음으로 — 메모 첫 줄의 세 키워드 정리

### 데이터 드리븐 (Data-Driven)

- **정의**: 게임의 규칙·수치·구성을 **코드에 하드코딩하지 않고 외부 데이터로 분리**하는 설계
- **효과**: 기획자가 프로그래머 없이 밸런스를 조정 / 빌드 없이 패치(핫픽스) / 코드 수정 없이 콘텐츠 추가
- **파일 시스템 역사와의 연결**: 1960년대에 "포맷이 바뀌면 코드를 고쳐야 했다"는 문제를 RDB가 **스키마 + DBMS**로 풀었고, 게임은 같은 문제를 **마스터 데이터 테이블 + 파서/코드 자동 생성**으로 풉니다. 문제의식이 동일합니다.
- **전형적 파이프라인**: `Excel(기획) → 검증 스크립트 → 바이너리/JSON + C# 클래스 자동 생성 → 클라이언트 배포`

### 세이브 / 로드

- **정의**: 메모리의 런타임 상태를 **영속 저장소**로 직렬화/역직렬화하는 것
- **DB 개념 대응**: 원자성(임시 파일+rename), 지속성(fsync), 스키마 마이그레이션(version 필드), 무결성(값 범위 검증 + 서명)
- **선택**: 싱글 = 로컬 파일/SQLite, 온라인 = 서버 RDB (**클라이언트 로컬 세이브는 신뢰 불가** — 치트)

### MVVM

- **정의**: **Model**(데이터·비즈니스 로직) / **View**(화면) / **ViewModel**(View용으로 가공한 상태 + 커맨드) 로 나누는 UI 아키텍처
- **핵심 가치**: **데이터 바인딩**으로 View와 상태를 동기화 → View가 Model을 직접 모름 → 테스트 가능·교체 가능
- **DB와의 연결**: 데이터 소스가 파일이든 로컬 DB든 서버 API든, **ViewModel 이하의 계층만 바뀌고 View는 그대로**입니다. 이건 3장에서 본 **논리적/물리적 데이터 독립성** 과 정확히 같은 발상입니다.
- 실제 계층: `DB/API → Repository(DAO) → Model → ViewModel → (Binding) → View`

> **세 키워드를 한 문장으로** _"데이터를 코드 밖으로 빼서(데이터 드리븐), 안전하게 남기고 되살리며(세이브·로드), 화면과도 분리한다(MVVM). 파일 시스템의 데이터 종속성 문제를 DBMS가 풀었던 것과 같은 원칙을, 게임 클라이언트 설계에 적용한 것."_

## 12. 면접 대비 — 빈출 질문 & 한 줄 답

| 질문                   | 핵심 답                                                                     |
| -------------------- | ------------------------------------------------------------------------ |
| 파일 시스템 대비 DBMS의 장점?  | 데이터 독립성, 중복·불일치 제거, 무결성·보안 강제, 동시성 제어, 장애 복구                             |
| 데이터 독립성이란?           | 저장 구조(내부 스키마)나 논리 구조(개념 스키마)가 바뀌어도 응용프로그램을 수정하지 않아도 되는 성질. 3단계 스키마로 구현   |
| 관계형 DB의 "관계"란?       | 테이블 간 연결이 아니라 **릴레이션 = 튜플의 집합 = 테이블 그 자체** (수학적 관계)                      |
| 트랜잭션이란? ACID?        | 쪼갤 수 없는 논리적 작업 단위. 원자성/일관성/격리성/지속성                                       |
| 격리 수준을 올리면?          | 이상 현상은 줄지만 락 경합으로 동시 처리량이 떨어짐                                            |
| 정규화의 목적? 역정규화는 왜?    | 중복 제거로 갱신 이상 방지 / 조인 비용을 줄여 읽기 성능을 얻기 위해                                 |
| 인덱스의 장단점?            | 조회 O(log n)으로 빨라지지만, 저장 공간 + INSERT/UPDATE/DELETE 시 인덱스 갱신 비용            |
| RDB vs NoSQL 선택 기준?  | 무결성·트랜잭션·복잡한 조인이 필요하면 RDB / 초대량 쓰기·유연한 스키마·수평 확장이 필요하면 NoSQL             |
| CAP 정리?              | 분산 시스템은 C·A·P 중 2개만. 분할은 불가피하므로 실질적으로 일관성 vs 가용성의 선택                     |
| 게임에 RDB를 쓰는 이유?      | 재화·아이템은 트랜잭션과 무결성이 필수. 아이템 복사/소멸 버그는 결과적 일관성으로 감당 불가                     |
| 그럼 게임은 RDB만 쓰나?      | 아니요. RDB(계정·재화) + Redis(랭킹·세션·캐시) + 로그 DW(분석) + 파일/SQLite(마스터 데이터) 하이브리드 |
| DB의 수평 확장이 어려운 이유?   | 조인과 트랜잭션이 노드를 넘으면 비용 폭발(분산 트랜잭션). 그래서 샤딩하고 샤드 간 조인을 포기                   |
| 마스터 데이터와 유저 데이터의 차이? | 마스터 = 패치 시에만 바뀌는 읽기 전용 기획 데이터, 클라 배포 / 유저 = 실시간 변경, 서버 DB                |
