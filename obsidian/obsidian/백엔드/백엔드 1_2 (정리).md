# DB 정리 노트 ② — 스키마 / 필드 / DB의 단위 / SQL

> **🔧 정정** = 잘못 이해한 부분, **➕ 보충** = 빠진 부분

---

## 1. 스키마(Schema)란?

> **스키마 = 데이터베이스의 구조와 제약조건을 정의한 것. 한마디로 "설계도".**

무엇이 스키마에 들어가는가:

- 어떤 **테이블**이 있는지
- 각 테이블에 어떤 **컬럼**이 있고, 각 컬럼의 **자료형**은 무엇인지
- 어떤 컬럼이 **키(PK/FK/UK)** 인지
- 어떤 **제약조건**(NOT NULL, UNIQUE, DEFAULT, CHECK)이 걸려 있는지
- 테이블 간의 **관계(relationship)**

### 스키마 vs 인스턴스 (면접 빈출)

| |스키마 (Schema)|인스턴스 (Instance)|
|---|---|---|
|뜻|구조·틀의 정의|**특정 시점**의 실제 데이터 값|
|비유|클래스 정의 / 설계도|객체(인스턴스) / 실제 건물|
|변화|거의 안 바뀜 (정적)|계속 바뀜 (동적)|
|예|`users(id INT, name VARCHAR(20), level INT)`|`(1, 'daniel', 100)`|

### 3단계 스키마 (ANSI/SPARC) — 노트 ①의 데이터 독립성과 연결

| 단계  | 이름                | 관점                                     |
| --- | ----------------- | -------------------------------------- |
| 외부  | External Schema   | 각 사용자·앱이 보는 뷰 (여러 개 존재)                |
| 개념  | Conceptual Schema | 조직 전체의 통합 논리 구조 ← **보통 "스키마"라고 하면 이것** |
| 내부  | Internal Schema   | 실제 물리 저장 구조 (파일, 인덱스, 페이지)             |

### ⚠️ 헷갈리는 지점 — "스키마"는 DBMS 제품마다 뜻이 다릅니다

|DBMS|"스키마"의 의미|
|---|---|
|**MySQL / MariaDB**|**데이터베이스와 완전 동의어.** `CREATE SCHEMA` = `CREATE DATABASE`|
|**PostgreSQL**|데이터베이스 **안의 네임스페이스**. 기본값 `public`. → `database > schema > table`|
|**Oracle**|**사용자(User)가 소유한 객체들의 집합.** 계정 = 스키마|
|**SQL Server**|데이터베이스 안의 네임스페이스. 기본값 `dbo`|

👉 MySQL만 쓰면 "스키마 = DB"로 이해해도 무리가 없지만, PostgreSQL을 만나면 한 단계가 더 끼어 있다는 걸 기억하세요. 면접에서 "스키마가 뭐죠?"라는 질문에는 **"논리적 설계도"** 라는 개념적 답을 먼저 하고, 제품별 차이를 덧붙이면 좋습니다.

## 2. 필드(Field)란?

> **필드 = 컬럼(열) = 속성(Attribute).** 같은 것을 다른 문맥에서 부르는 이름입니다.

|부르는 이름|어디서 쓰는 용어|
|---|---|
|**필드 (Field)**|파일 시스템 시대 / 일반 프로그래밍|
|**속성 (Attribute)**|관계 모델(이론) 용어|
|**컬럼 (Column)**|SQL / 실무 용어 ← 실무에서 가장 정확|

엄밀히 구분하면:

- **컬럼** = 세로줄 **전체** (`name` 컬럼)
- **필드** = 한 레코드 안의 **한 칸**(셀) 을 가리키는 용도로도 쓰임 (`1번 유저의 name 필드 = 'daniel'`)

실무에서는 거의 혼용하니 크게 신경 쓰지 않아도 되지만, **"컬럼"으로 통일해 말하는 게 가장 안전**합니다.

## 3. DB의 단위 — 계층 구조

### 🔧 노트를 정정·확장한 전체 계층

```
서버 / 인스턴스 (DB 프로세스 하나)
 │
 └─ 데이터베이스 (Database)          ← MySQL에서는 = 스키마
     │
     ├─ 테이블 (Table)               ← 2차원 구조 (행 × 열)
     │   ├─ 컬럼 (Column/필드/속성)  ← 【구조】 = 스키마
     │   └─ 행 (Row/레코드/튜플)     ← 【데이터】 = 인스턴스
     │        └─ 필드값 (셀)
     │
     ├─ 인덱스 (Index)
     ├─ 뷰 (View)
     ├─ 저장 프로시저 / 함수
     ├─ 트리거 (Trigger)
     └─ 제약조건 (Constraint)
```

> **🔧 정정 — 테이블은 "행으로만" 이루어진 게 아닙니다.** 노트에 _"table → data 들(행으로 이루어짐)"_ 이라고 되어 있는데, 테이블은 **행(row)과 열(column)의 2차원 구조**입니다. 그리고 이 둘은 성격이 완전히 다릅니다.
> 
> - **열(컬럼)** = 구조. 미리 정의되고 거의 안 바뀜 → **스키마**
> - **행(로우)** = 데이터. 계속 추가·수정·삭제됨 → **인스턴스**
> 
> 이 구분이 "RDB는 엄격한 스키마를 요구한다"는 말의 정확한 의미입니다. **열을 먼저 확정해야 행을 넣을 수 있다**는 뜻이죠.

> **➕ 보충 — 데이터베이스 안에는 테이블만 있는 게 아닙니다.** 노트에는 `database → table`만 있는데, 인덱스·뷰·프로시저·트리거도 DB의 객체(Object)입니다. `CREATE`의 대상이 "데이터베이스, 테이블, 인덱스 **등**"이라고 쓴 게 이걸 가리킵니다.

### ➕ 보충 — 용어 대응표 (이론 ↔ 실무)

|관계 모델 (이론)|SQL (실무)|파일 시스템 시대|
|---|---|---|
|릴레이션 (Relation)|테이블|파일|
|튜플 (Tuple)|행 / 로우|레코드|
|속성 (Attribute)|열 / 컬럼|필드|
|도메인 (Domain)|자료형 + 제약조건|—|
|차수 (Degree)|컬럼의 개수|—|
|카디널리티 (Cardinality)|행의 개수|—|

## 4. ➕ 보충 — 키(Key)

컬럼 이야기가 나왔으니 반드시 붙어야 하는 개념입니다.

|키|의미|
|---|---|
|**슈퍼키**|행을 유일하게 식별하는 컬럼 조합 (불필요한 컬럼이 섞여도 됨)|
|**후보키 (Candidate Key)**|슈퍼키 중 **최소성**을 만족하는 것|
|**주키 (Primary Key)**|후보키 중 선택한 **대표 키.** NULL 불가 + 중복 불가|
|**대체키 (Alternate Key)**|후보키 중 PK로 선택되지 **않은** 것|
|**외래키 (Foreign Key)**|다른 테이블의 PK를 참조 → **참조 무결성** 보장|
|**유니크키 (Unique)**|중복 불가, 단 **NULL은 허용** (PK와의 차이)|

> **게임 예시**: `users` 테이블에서 `user_id`(PK, AUTO_INCREMENT), `email`(UNIQUE), `nickname`(UNIQUE). `characters` 테이블의 `user_id`는 `users.user_id`를 참조하는 FK.
> 
> **실무 팁**: PK는 닉네임 같은 "의미 있는 값"(자연키)보다 **의미 없는 정수/UUID(인조키, Surrogate Key)** 를 쓰는 게 정석입니다. 닉네임은 변경될 수 있고, FK로 퍼져 있으면 변경 비용이 폭발합니다.

## 5. ➕ 보충 — 자료형과 제약조건

### 게임 개발에서 꼭 알아야 할 자료형

|자료형|용도|주의|
|---|---|---|
|`INT` / `BIGINT`|ID, 레벨, 카운트|유저 수가 21억을 넘을 수 있으면 `BIGINT`|
|`VARCHAR(n)` / `CHAR(n)`|문자열|VARCHAR=가변, CHAR=고정. 닉네임은 VARCHAR|
|`DECIMAL(p,s)`|**돈, 유료 재화**|⚠️ 아래 참고|
|`FLOAT` / `DOUBLE`|좌표, 확률, 물리값|오차 허용되는 곳에만|
|`DATETIME` / `TIMESTAMP`|시각|TIMESTAMP는 UTC 저장 + 타임존 변환|
|`TINYINT(1)` / `BOOLEAN`|참/거짓 (`isDeleted` 등)|MySQL은 BOOLEAN = TINYINT(1)|
|`JSON`|가변 구조 부가 데이터|남용 금지 (인덱싱·조회 불리)|

> ⚠️ **절대 규칙: 돈과 재화에 `FLOAT`을 쓰지 마세요.** 부동소수점은 `0.1 + 0.2 != 0.3` 입니다. 정산이 1원씩 어긋나기 시작합니다. **`DECIMAL`을 쓰거나, 아예 정수(최소 단위)로 저장**하세요. 게임 재화는 보통 `BIGINT`로 개수를 세는 게 가장 안전합니다.

### 제약조건 (Constraint)

|제약조건|의미|
|---|---|
|`NOT NULL`|NULL 금지|
|`UNIQUE`|중복 금지 (NULL 허용)|
|`PRIMARY KEY`|NOT NULL + UNIQUE|
|`FOREIGN KEY`|참조 대상에 실제 존재하는 값만|
|`DEFAULT`|값 생략 시 기본값|
|`CHECK`|값의 범위·조건 (예: `level BETWEEN 1 AND 100`)|
|`AUTO_INCREMENT`|자동 증가 (Oracle은 시퀀스, PG는 SERIAL/IDENTITY)|

> **➕ NULL의 의미** (면접 빈출) `NULL`은 **"값이 없음/알 수 없음"** 입니다. `0`도 아니고 빈 문자열 `''`도 아닙니다.
> 
> - 비교는 `= NULL`이 아니라 **`IS NULL` / `IS NOT NULL`**
> - `NULL`과의 산술·비교는 결과가 `NULL` → **3값 논리**(TRUE/FALSE/UNKNOWN)
> - `COUNT(컬럼)`은 NULL을 세지 않지만 `COUNT(*)`는 셉니다

## 6. SQL이란

> **SQL (Structured Query Language) = 관계형 DB와 대화하는 표준 언어.**

특징: **선언형(Declarative)** 언어입니다. "어떻게 찾아라"가 아니라 **"무엇을 원한다"** 를 씁니다. 실제 탐색 경로(인덱스를 쓸지, 조인 순서를 어떻게 할지)는 DBMS의 **옵티마이저**가 결정합니다. 그래서 같은 SQL이 데이터 양과 인덱스에 따라 성능이 100배 차이 날 수 있습니다.

### 🔧 SQL의 분류 — 노트에 DDL·DML만 있는데, 4가지입니다

|분류|이름|명령어|커밋/롤백|
|---|---|---|---|
|**DDL**|데이터 정의어|`CREATE` `ALTER` `DROP` `TRUNCATE` `RENAME`|**자동 커밋, 롤백 불가**|
|**DML**|데이터 조작어|`INSERT` `UPDATE` `DELETE` (`SELECT`)|**롤백 가능**|
|**DCL**|데이터 제어어|`GRANT` `REVOKE`|권한 부여/회수|
|**TCL**|트랜잭션 제어어|`COMMIT` `ROLLBACK` `SAVEPOINT`|트랜잭션 확정/취소|

- `SELECT`만 따로 **DQL(Data Query Language)** 로 분류하는 교재도 있습니다. 어느 쪽이든 틀린 건 아니니, 물으면 "보통 DML에 포함하지만 DQL로 따로 보기도 한다"고 답하면 됩니다.
- **DDL은 롤백이 안 된다**는 점이 노트의 "DROP은 위험하다"를 뒷받침하는 정확한 근거입니다.

## 7. DDL — 데이터 정의어

노트 내용은 대체로 정확합니다. 정정·보충만 짚습니다.

### CREATE

```sql
CREATE TABLE users (
    user_id     BIGINT       NOT NULL AUTO_INCREMENT,
    nickname    VARCHAR(20)  NOT NULL,
    level       INT          NOT NULL DEFAULT 1,
    gold        BIGINT       NOT NULL DEFAULT 0,
    is_deleted  TINYINT(1)   NOT NULL DEFAULT 0,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id),
    UNIQUE KEY uk_nickname (nickname),
    INDEX idx_level (level)
);
```

### ALTER — 🔧 "런칭 후엔 바꿀 일이 없는 게 맞다"는 절반만 맞습니다

> 노트: _"기획 단계에서 DB 스키마를 탄탄하게 완료하고, 서비스 런칭 후에는 컬럼 자체를 변경할 일이 없는 게 맞음"_

**"위험하다"는 판단은 100% 맞습니다.** 다만 **"변경할 일이 없는 게 맞다"** 는 현실과 다릅니다.

라이브 게임은 시즌마다 신규 콘텐츠가 들어오고, 그때마다 컬럼이나 테이블이 **반드시** 늘어납니다. 3년 서비스한 게임의 스키마가 런칭 때와 같은 경우는 없습니다. 그래서 실무의 목표는 **"ALTER를 안 하는 것"이 아니라 "ALTER를 안전하게, 무중단으로 하는 절차를 갖추는 것"** 입니다.

**① 작업의 위험도는 종류마다 다릅니다**

|작업|위험도|이유|
|---|---|---|
|컬럼 추가 (nullable 또는 DEFAULT)|낮음|기존 쿼리 영향 없음. Online DDL 지원|
|인덱스 추가|중간|생성 중 부하. 야간 작업 권장|
|컬럼 **타입 변경**|**높음**|테이블 전체 재구성 + 락 + 데이터 손실 가능|
|컬럼 **이름 변경 / 삭제**|**높음**|기존 애플리케이션 코드가 즉시 깨짐|

**② Expand–Migrate–Contract 패턴** (무중단 스키마 변경의 정석)

컬럼을 **바꾸는** 게 아니라, **늘렸다가 → 옮기고 → 줄입니다.**

```
1. Expand   새 컬럼을 추가 (기존 컬럼은 그대로 둔다)
2. 이중 쓰기 앱이 두 컬럼에 모두 쓴다 (배포)
3. Migrate  과거 데이터를 배치로 새 컬럼에 복사
4. 읽기 전환 앱이 새 컬럼만 읽는다 (배포)
5. Contract 충분히 지난 뒤 구 컬럼 제거
```

→ 각 단계가 독립 배포 가능하고, 어느 단계에서든 되돌릴 수 있습니다.

**③ 도구로 관리합니다** (기억해두면 좋은 이름들)

- **무중단 ALTER**: MySQL `ALGORITHM=INPLACE`(Online DDL), `gh-ost`(GitHub), `pt-online-schema-change`
- **스키마 버전 관리(마이그레이션)**: Flyway, Liquibase, EF Core Migrations, Alembic → 스키마 변경을 **코드처럼 Git으로 버전 관리**합니다. "누가 언제 무엇을 바꿨는지"가 남고, 개발/스테이징/운영 DB를 같은 상태로 맞출 수 있습니다.
- **대안**: 기존 테이블을 건드리기 싫으면 **1:1 확장 테이블을 새로 만들어 조인**합니다. 예: `users`를 그대로 두고 `user_season_stats`를 추가.

### DROP — 노트 내용이 아주 좋습니다. 근거만 보강

노트의 판단이 모두 실무 정석입니다.

- ✅ **라이브에서는 권한으로 원천 차단** → 아래 "권한 분리"가 이걸 구현하는 방법입니다
- ✅ **테이블을 `_old` / `_deleted` 로 리네임** → `RENAME TABLE`은 즉시 끝나고 되돌리기도 쉬움. "며칠 지켜본 뒤 정말 아무도 안 쓰면 DROP"
- ✅ **`isDeleted` 플래그 (Soft Delete)** → 정확합니다. 단, 아래 주의점 참고
- ✅ **제거 전 스냅샷(백업) 필수** → DDL은 롤백이 안 되니 백업이 유일한 되돌리기 수단

> **➕ 보충 — 권한 분리가 핵심입니다** (노트의 "권한 제한"을 구체화) 애플리케이션이 접속하는 DB 계정에는 **DDL 권한을 주지 않습니다.**
> 
> ```sql
> -- 앱용 계정: DML만
> GRANT SELECT, INSERT, UPDATE, DELETE ON gamedb.* TO 'app_user'@'%';
> -- 마이그레이션용 계정: DDL 포함, CI/CD만 사용
> GRANT ALL ON gamedb.* TO 'migrator'@'10.0.%';
> ```
> 
> 이렇게 하면 앱에 SQL 인젝션 취약점이 있어도 `DROP TABLE`은 애초에 실행되지 않습니다.

> **➕ 보충 — Soft Delete의 주의점** (노트에 적은 `isDeleted` 방식) 좋은 패턴이지만 대가가 있습니다.
> 
> - 모든 조회에 `WHERE is_deleted = 0`을 빼먹으면 **삭제된 데이터가 노출**됩니다 → 뷰(View)로 감싸거나 ORM의 글로벌 필터를 씁니다
> - `UNIQUE` 제약과 충돌: 닉네임을 soft delete 해도 UNIQUE가 살아 있어 **같은 닉네임을 다시 못 씁니다** → 복합 유니크(`nickname + deleted_at`)나 닉네임 뒤에 suffix를 붙이는 식으로 처리
> - 테이블이 계속 커집니다 → 오래된 건 **아카이브 테이블로 이관**
> - 개인정보(GDPR 등)는 soft delete로 부족합니다. **실제 파기 의무**가 있는 데이터는 하드 삭제 또는 익명화

### TRUNCATE — 🔧 "넘어가자"는 건 아쉽습니다. 면접에 아주 자주 나옵니다

노트의 판단("통째로 날릴 상황이 있어선 안 된다")은 **운영 DB에 대해서는 맞습니다.** 하지만 두 가지 이유로 알아둬야 합니다.

**① 실제로 쓰는 곳이 있습니다**

- 개발/테스트 환경 **초기화** (테스트마다 데이터 리셋)
- 매번 전체를 새로 채우는 **마스터 데이터 테이블 리로드**
- 임시/스테이징 테이블 비우기

**② `DELETE`와의 차이가 단골 면접 질문입니다**

| |`DELETE FROM t;`|`TRUNCATE TABLE t;`|`DROP TABLE t;`|
|---|---|---|---|
|분류|**DML**|**DDL**|DDL|
|롤백|**가능**|**불가 (자동 커밋)**|불가|
|WHERE 조건|가능|**불가 (전체만)**|—|
|속도|느림 (행 단위 + 로그)|**매우 빠름** (데이터 페이지 해제)|빠름|
|테이블 구조|남음|**남음**|**사라짐**|
|AUTO_INCREMENT|**유지됨**|**1로 초기화**|—|
|트리거|동작함|**동작 안 함**|—|

👉 한 줄 정리: **DELETE = 지우개(되돌리기 가능), TRUNCATE = 공책 한 장 찢기, DROP = 공책 버리기.**

## 8. DML — 데이터 조작어

노트의 예시와 CRUD 매핑은 모두 정확합니다. 실무 주의점을 보강합니다.

### SELECT

```sql
SELECT user_id, nickname, level        -- 필요한 컬럼만
FROM   users
WHERE  level > 10
  AND  is_deleted = 0
ORDER BY level DESC
LIMIT  100;
```

> **➕ `SELECT *` 는 실무에서 지양합니다.** 노트의 `SELECT * FROM users WHERE level > 10;` 은 학습용으로는 완벽하지만, 실제 코드에서는 **필요한 컬럼만** 명시합니다.
> 
> - 불필요한 네트워크·메모리 전송 (특히 `TEXT`/`BLOB` 컬럼이 딸려 옴)
> - **커버링 인덱스**를 못 타서 느려짐
> - 나중에 컬럼이 추가되면 애플리케이션이 예상 못 한 데이터를 받음

> **➕ SELECT의 논리적 실행 순서** (면접 빈출 — 작성 순서와 다릅니다)
> 
> ```
> FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
> ```
> 
> 그래서 이런 규칙이 나옵니다.
> 
> - `WHERE`는 그룹화 **전** 필터, `HAVING`은 그룹화 **후** 필터 (`HAVING COUNT(*) > 1`)
> - `SELECT`에서 만든 **별칭(alias)은 `WHERE`에서 쓸 수 없고** `ORDER BY`에서는 쓸 수 있습니다

> **➕ JOIN 최소 정리**
> 
> |종류|결과|
> |---|---|
> |`INNER JOIN`|양쪽 모두 매칭되는 행만|
> |`LEFT JOIN`|왼쪽 전체 + 매칭되는 오른쪽 (없으면 NULL)|
> |`RIGHT JOIN`|그 반대|
> |`FULL OUTER JOIN`|양쪽 전체 (MySQL 미지원 → UNION으로 우회)|
> 
> 예: `SELECT u.nickname, i.item_name FROM users u LEFT JOIN inventory i ON u.user_id = i.user_id;` → 인벤토리가 빈 유저도 결과에 나옵니다. `INNER JOIN`이면 빠집니다.

### INSERT

```sql
INSERT INTO users (nickname, level) VALUES ('daniel', 100);
```

> **🔧 사소한 것 — 따옴표** 노트에 `'daniel'` 처럼 곡선 따옴표(스마트 쿼트)가 들어가 있습니다. 문서 편집기가 자동 변환한 것인데, **SQL에서는 반드시 직선 따옴표 `'`** 여야 합니다. 곡선 따옴표를 그대로 붙여넣으면 문법 오류가 납니다. 코드는 코드 에디터에서 쓰세요. 또 MySQL에서 **문자열은 `'단일'`, 식별자(컬럼·테이블명)는 백틱 `` `users` ``** 입니다. `"이중"`은 설정에 따라 뜻이 달라집니다.

> **➕ 보충 — INSERT 실무 패턴**
> 
> - **컬럼명은 반드시 명시**하세요. `INSERT INTO users VALUES (...)` 는 컬럼 순서에 의존해서 스키마가 바뀌면 조용히 깨집니다
> - **벌크 인서트**: `VALUES (...), (...), (...)` 로 묶으면 한 건씩 넣는 것보다 훨씬 빠릅니다
> - **UPSERT** (있으면 수정, 없으면 삽입) — 출석 체크·일일 카운터에 자주 씁니다
>     
>     ```sql
>     INSERT INTO daily_login (user_id, login_date, count)VALUES (1, '2026-09-22', 1)ON DUPLICATE KEY UPDATE count = count + 1;   -- MySQL
>     ```
>     
>     PostgreSQL은 `ON CONFLICT ... DO UPDATE`, 표준 SQL은 `MERGE`.

### UPDATE / DELETE — ⚠️ 여기가 실무 사고 1순위입니다

```sql
UPDATE users SET level = 2 WHERE name = 'daniel';
DELETE FROM users WHERE name = 'daniel';
```

노트의 예시는 정확합니다. 다만 **`WHERE`를 빼먹는 사고**가 현업에서 가장 흔한 대형 장애입니다.

```sql
UPDATE users SET level = 2;      -- 💀 전 유저의 레벨이 2가 됩니다
DELETE FROM users;               -- 💀 전 유저가 사라집니다
```

**방어 수단**

1. **트랜잭션으로 감싸고 먼저 확인**
    
    ```sql
    START TRANSACTION;SELECT COUNT(*) FROM users WHERE name = 'daniel';   -- 영향 행 수 확인UPDATE users SET level = 2 WHERE name = 'daniel';-- 결과가 예상과 같으면COMMIT;    -- 아니면 ROLLBACK;
    ```
    
    👉 `UPDATE`/`DELETE`는 **DML이라 ROLLBACK이 됩니다.** (DDL과의 결정적 차이)
2. **`SET sql_safe_updates = 1;`** — MySQL에서 키/인덱스 조건 없는 UPDATE/DELETE를 거부
3. **`LIMIT` 병용** — `DELETE FROM users WHERE ... LIMIT 1;`
4. 대량 삭제는 **한 번에 하지 말고 나눠서** — 수백만 행을 한 트랜잭션으로 지우면 락이 오래 걸리고 복제 지연이 발생합니다. `LIMIT 1000`으로 반복하세요
5. **운영 DB 직접 접속 금지.** 관리 도구/스크립트를 통하고, 실행 이력을 남깁니다

> **➕ SQL 인젝션 — 반드시 파라미터 바인딩** 문자열을 이어붙여 쿼리를 만들면 안 됩니다.
> 
> ```
> ❌ "SELECT * FROM users WHERE name = '" + input + "'"
>    → input 에 `' OR '1'='1` 을 넣으면 전체 조회
> ✅ "SELECT * FROM users WHERE name = ?"  + 파라미터로 값 전달
> ```
> 
> 언어별로 Prepared Statement / ORM의 파라미터 바인딩을 씁니다. 여기에 7장의 **권한 분리**를 더하면 이중 방어가 됩니다.

## 9. ➕ 보충 — DCL과 TCL

### DCL — 권한 제어

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON gamedb.* TO 'app_user'@'%';
REVOKE DELETE ON gamedb.* FROM 'app_user'@'%';
```

노트의 "DROP 권한 제한"이 바로 이 DCL로 구현됩니다. **최소 권한 원칙(Principle of Least Privilege)** — 각 계정에 꼭 필요한 권한만 줍니다.

### TCL — 트랜잭션 제어

```sql
START TRANSACTION;
  UPDATE users SET gold = gold - 1000 WHERE user_id = 1;
  UPDATE users SET gold = gold + 1000 WHERE user_id = 2;
COMMIT;      -- 또는 ROLLBACK;
```

- `COMMIT` — 변경 확정 (지속성 보장)
- `ROLLBACK` — 트랜잭션 시작 시점으로 되돌림
- `SAVEPOINT` — 중간 지점 저장, `ROLLBACK TO SAVEPOINT sp1;` 로 부분 롤백

> ⚠️ **자동 커밋(Autocommit)**: MySQL은 기본이 `autocommit = 1` 이라, `START TRANSACTION` 없이 실행한 `UPDATE`는 **즉시 확정되어 롤백할 수 없습니다.** 위험한 작업 전에 반드시 트랜잭션을 열거나 `SET autocommit = 0;` 을 하세요.

## 10. ➕ 보충 — 인덱스 한 줄 정리

컬럼·스키마 얘기의 마지막 조각입니다.

- **인덱스 = 책의 색인.** 전체를 훑지 않고 원하는 행을 `O(log n)`으로 찾게 해줌 (B+Tree)
- **거는 곳**: `WHERE` / `JOIN ON` / `ORDER BY` 에 자주 쓰는 컬럼
- **대가**: 저장 공간 증가 + `INSERT`/`UPDATE`/`DELETE` 때마다 인덱스도 갱신 → **쓰기가 느려짐**
- **PK는 자동으로 인덱스**(MySQL InnoDB는 클러스터드 인덱스)
- **카디널리티가 낮은 컬럼(성별, is_deleted 같은)에 단독 인덱스는 효과가 거의 없습니다**
- 실행 계획 확인: `EXPLAIN SELECT ...` → 인덱스를 타는지 `type`, `key` 컬럼으로 확인

## 11. 이 노트의 게임 스키마 예시 (전체를 묶어서)

```sql
-- 계정
CREATE TABLE users (
    user_id    BIGINT      NOT NULL AUTO_INCREMENT,
    email      VARCHAR(255) NOT NULL,
    created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id),
    UNIQUE KEY uk_email (email)
);

-- 캐릭터 (계정 1 : 캐릭터 N)
CREATE TABLE characters (
    char_id    BIGINT      NOT NULL AUTO_INCREMENT,
    user_id    BIGINT      NOT NULL,
    nickname   VARCHAR(20) NOT NULL,
    level      INT         NOT NULL DEFAULT 1,
    exp        BIGINT      NOT NULL DEFAULT 0,
    gold       BIGINT      NOT NULL DEFAULT 0,   -- 돈은 정수!
    is_deleted TINYINT(1)  NOT NULL DEFAULT 0,   -- Soft Delete
    PRIMARY KEY (char_id),
    UNIQUE KEY uk_nickname (nickname),
    INDEX idx_user (user_id),
    CONSTRAINT fk_char_user FOREIGN KEY (user_id) REFERENCES users(user_id)
);

-- 인벤토리 (캐릭터 1 : 아이템 N)
CREATE TABLE inventory (
    inv_id    BIGINT NOT NULL AUTO_INCREMENT,
    char_id   BIGINT NOT NULL,
    item_id   INT    NOT NULL,      -- 마스터 데이터의 아이템 ID (노트 ① 참고)
    quantity  INT    NOT NULL DEFAULT 1,
    PRIMARY KEY (inv_id),
    INDEX idx_char (char_id),
    CONSTRAINT fk_inv_char FOREIGN KEY (char_id) REFERENCES characters(char_id)
);
```

여기서 확인할 것:

- **`item_id`는 FK가 아닙니다.** 아이템 스펙은 **마스터 데이터**(Excel → 클라이언트 배포)이므로 DB에 테이블이 없을 수도 있습니다. 노트 ①의 "마스터 데이터 vs 유저 데이터" 구분이 스키마 설계에 그대로 나타납니다.
- `gold`가 `BIGINT`인 이유 → 5장의 FLOAT 경고
- `is_deleted`가 있는 이유 → 7장의 Soft Delete

## 12. 면접 대비 — 빈출 질문 & 한 줄 답

|질문|핵심 답|
|---|---|
|스키마란?|DB의 구조와 제약조건의 정의. "설계도". 외부/개념/내부 3단계|
|스키마와 인스턴스의 차이?|스키마 = 구조(정적, 클래스), 인스턴스 = 특정 시점의 실제 데이터(동적, 객체)|
|필드 = ?|컬럼(열) = 속성. 파일 시스템 용어가 필드, 이론 용어가 속성, SQL 용어가 컬럼|
|PK와 UNIQUE의 차이?|둘 다 중복 불가. PK는 **NULL 불가 + 테이블당 1개**, UNIQUE는 **NULL 허용 + 여러 개 가능**|
|DDL / DML / DCL / TCL?|정의 / 조작 / 권한 / 트랜잭션. **DDL은 자동 커밋으로 롤백 불가**|
|DELETE vs TRUNCATE vs DROP?|DML·롤백 가능·WHERE 가능 / DDL·롤백 불가·전체·AUTO_INCREMENT 초기화 / 테이블 자체 삭제|
|운영 중 ALTER가 위험한 이유와 대안?|테이블 재구성 + 락 → 다운타임. Online DDL·gh-ost, Expand-Migrate-Contract, 마이그레이션 도구로 버전 관리|
|DROP을 막는 방법?|앱 계정에 DDL 권한 미부여(DCL), 리네임 + soft delete, 사전 백업|
|SELECT의 논리적 실행 순서?|FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT|
|WHERE와 HAVING의 차이?|WHERE = 그룹화 전 행 필터, HAVING = 그룹화 후 그룹 필터|
|`SELECT *` 를 왜 지양?|불필요한 전송, 커버링 인덱스 불가, 스키마 변경에 취약|
|NULL 비교는?|`= NULL` 안 됨. `IS NULL` / `IS NOT NULL`. 3값 논리|
|SQL 인젝션 방어?|문자열 연결 금지, Prepared Statement로 파라미터 바인딩 + 최소 권한 원칙|
|인덱스의 트레이드오프?|읽기는 O(log n)으로 빨라지지만 저장 공간 + 쓰기 비용 증가|
|돈/재화 컬럼의 자료형?|`FLOAT` 금지(부동소수점 오차). `DECIMAL` 또는 최소 단위 정수(`BIGINT`)|
